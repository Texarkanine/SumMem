# TASK ARCHIVE: read-once

## SUMMARY

Rework of [PR #95](https://github.com/Texarkanine/SumMem/pull/95) on `feat/fold-grain-as-child` (from head dd16eac). `note` and `nap` now read and digest each nap children file (`.tree`) at most once per command. Heal, the fold scan, and `nap` share one parse, `_as_child`'s, which is the same parse whose refusals decide what `nap` can fold (#88). The parse is cached only while `with_store_lock` holds the store lock. Heal's raw-JSON walk (`_digests_of_dict`, from #51) is gone. At 4094 leaves, `.tree` reads per command went from 22 to 11 for `note` and from 34 to 12 for `nap`, and in-process `nap` time is roughly halved. `summem` is 8 lines shorter than at dd16eac.

## IMPLEMENTATION

Baseline at dd16eac: `note` read every `.tree` twice (heal's `leaf_digests` raw-JSON walk, then `_fold_grains` via `_as_child`). `nap` read up to three times (heal, `write_nap`'s nearer-twin `_fold_grains`, then `fold_request` re-listing and scanning again).

A throwaway process-wide path cache halved reads but broke 10 tests. Nine edit a `.tree` or `.summ` in place between direct calls, so a cache that outlives one command is stale. The tenth pinned heal's raw-JSON walk. That moved the cache scope to the lock window.

Changes in [`summem`](../../../summem):
- `_CHILDREN: dict | None`, `None` outside the lock. `with_store_lock` sets it to `{}` and resets it in `finally`. Its docstring says why the cache is safe: only this process writes under the lock, and `_replace_bytes` forgets each write.
- `_as_child` (nap branch) caches `(inner Tree, digests)` or `None` (on `_TREE_PARSE_ERRORS`), keyed on `tree_path`. It builds `NapChild` from the current node on every call, so captions are never cached. The `is_file()` "unknown id" check stays ahead of the cache.
- `_replace_bytes`, the only store writer, drops `dest` from the cache, so a heal-repaired `.tree`, a rematerialized `.summ`, or a write over a lying stem is parsed fresh.
- `leaf_digests` reads through `_as_child`. `_digests_of_dict` is deleted.
- Net −8 lines from dd16eac (+36 −44; the lock body was re-indented).

Other files:
- [`tests/test_zipper.py`](../../../tests/test_zipper.py): `test_cli_note_reads_each_children_file_once` and `test_cli_nap_reads_each_children_file_once` (helpers `_over_budget_naps`, `_count_tree_reads`) spy `Path.read_bytes` and assert no `.tree` path is read twice. `test_leaf_digests_nap_does_not_build_tree` is deleted, because heal now shares nap's parse on purpose.
- [`docs/architecture/index.md`](../../../docs/architecture/index.md): one sentence in the Zipper lock paragraph.
- [`memory-bank/productContext.md`](../../productContext.md): script size and cost constraint. [`memory-bank/systemPatterns.md`](../../systemPatterns.md): one parse per children file under the lock, and every write goes through `_replace_bytes`.
- `.summem/`: notes for the operator norm, the cache-scope gotcha, and a superseding note that heal no longer walks raw JSON (#51 reversed, #88). Plus the naps the driver asked for.

Declined: preflight run 2's write-through cache. It adds lines, and the benchmark has no heal split to justify them.

## LESSONS LEARNED

- In this driver, "content-addressed path means fixed bytes" holds across commands but not inside one. Heal rematerializes a missing half of a pair. A per-command cache must be invalidated at the single writer (`_replace_bytes`), not justified by content addressing.
- The tests treat the module as a library and edit store files between direct calls. Any memoization must be scoped to a CLI-command window, or tests go stale even though production processes run one command each.
- When a change reverses an earlier recorded decision (here #51's raw-JSON heal), record the superseding SumMem note in the same change. Otherwise wake keeps advertising the old design.

## PROCESS IMPROVEMENTS

- On this WSL machine, subprocess timing drifts by tens of ms between back-to-back blocks. Interleave drivers round-robin and also time `main()` in-process, or a real 30–50% gain can look like noise.
- Running a throwaway prototype against the full suite before planning found the cache-scope constraint in one step.

## TECHNICAL IMPROVEMENTS

- If one parse per command had been foundational, a mutating command would load the view once, with each row owning its parsed children lazily, and heal and `nap` would update that view as they write instead of re-listing after every mutation. The re-list is the root cause of the repeated reads. The lock-scoped cache is the smallest retrofit and gets the same read count without changing `heal_view`, `write_nap`, or `fold_request` signatures.
- Advisory, no action: `_CHILDREN` is set before the flock is taken, and a nested lock would turn the cache off for the rest of the outer call. Neither matters today.
- A write-through cache in `rematerialize_child` and `write_nap` would spare a post-merge heal from reparsing kids it just wrote (about 2–3 lines). Re-measure a merge-heal case first.
