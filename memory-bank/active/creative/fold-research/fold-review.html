Middle orphans: which fold rule, and what each answer costs

SumMem · branch middle-orphans · 2026-10-06 · nothing implemented — evidence is red tests, scratch prototypes, and simulation on the real driver

01Plan summary

The fold request today only pairs two equal-grain rows that sit next to each other. That works for one writer. With several writers, merges and repairs leave an older row next to a bigger newer one — a wall. The row before the wall never meets an equal neighbor again, and neither does anything older. Those wake lines are dead for good.

Problem

Five ways a wall forms, each now a red test in tests/test_middle_orphans.py: a merged branch that never saw an older note; a late note; a zipper reopen; surgery; a pack whose grain is not a power of two.

Core idea

Nap the oldest row that has a row of the same grain anywhere below it, with the nearest such row. One sentence, no cases. Grains stay powers of two.

Scope

  • Fold picker (fold_request)
  • Decision 2 — which pairs nap accepts
  • Decision 3 — wake's expanded row order
  • Decision 4 — legacy packs whose grain isn't 2ᵏ
  • Docs and test fixtures that assume neighbors

Where each rule ends up

The case that separates them: a young main, then a big branch

Main holds [4, 1]. A branch that never saw those five notes folds its own eight into an 8-pack and merges. Nothing older is an 8, and nothing newer can reach the 4 or the 1 without jumping over the 8. Then 64 more notes arrive at budget 4.

What your pull-back rule gets right, and where it breaks. On your example it does exactly the three moves you described — pull the 4 back, pull the 2 back, then fold "4, 1, 1" into "4, 2" — with the smallest jumps. But it never lets a small old row move toward a bigger newer one, so the young-main case stays stranded forever, and in the multi-writer runs (§4) each stranded row gets jumped over again by every later pull-back. The recommended rule takes one bigger jump early instead.

05Decision 2 — which pairs may nap fold?

Your intuition: yes — same grain, and no row of that grain between them. My read: the "same grain" half is required by "never write a non-power-of-two pack"; the "nearest" half is a cheap guard with no known cost.

Product ramifications

  • nap newly accepts two ids that are not neighbors in wake.
  • nap newly refuses unequal grains, and a same-grain pair with a nearer one between.
  • Help and docs change: "fold two adjacent ids" (summem:1387, README.md:152), "two adjacent notes" (README.md:160).
  • Error text not adjacent. Nap two ids that sit next to each other in wake. (summem:848) is replaced; pinned in tests/test_nap.py:233, :357, tests/test_cli.py:405.
  • Race: a merge between a fold request and the agent's nap can put a row between the pair → refused. Same class as today's "not adjacent"; the next note asks again.
  • This is a narrowing of a CLI command — choose fix: vs feat: deliberately for Release Please.

Algorithm ramifications

  • Closure: notes are grain 1; equal folds double → every pack written is 2ᵏ, forever.
  • Balance: tree depth = log₂(grain). Simulation: depth 10 at ~1,500 notes.
  • Bound: rows with all-distinct grains ≤ ⌊log₂N⌋+1, so the picker always finds a pair over budget.
  • "Nearest" blocks the one move that only adds misordering: pairing across a closer partner.
  • Error order: check grain after loading children, so unknown id / unreadable pack still win (4 tests depend on it).
  • 16 tests build unequal packs today: 12 through gitutil.fold_ids (7 calls in 4 files), which folds left-to-right into 3-, 5-, 7-packs; 4 zipper tests through the ABD/ABE shape, a 2-pack napped with a note on purpose.

06Decision 3 — wake sorts expanded rows by date

Your intuition: yes. My read: yes — it's display-only, broke no existing test in a prototype, and changes nothing in any store on this machine today. It only helps when wake expands, which is when the listing is shorter than the budget.

A skip pack, opened by wake (notes dated Jan 1–5)

Product ramifications

  • When wake opens packs, every printed row lands at its date. A skip pack's newer child moves below the rows it jumped; interleaved branch packs unscramble too.
  • At or over budget wake opens nothing, so nothing changes. All 22 stores on this machine are at budget or have nothing to open: zero visible change today.
  • A pack that stays closed still sits at its oldest note; its newer notes show only through its caption. The sort can't fix that — the picker's small jumps are what keep it small.
  • zoom is unchanged: it prints a pack's own two children.
  • Docs: "replace the newest expandable nap with its two children" (docs/architecture/index.md:165) gains "then sort by date".

Algorithm ramifications

  • In memory only — no extra file reads, wake stays wait-free.
  • Needs a full order key: ProjectedNode (summem:185) carries a seconds-only stamp. Carry the oldest note's stamp-rand (from _projected_child, summem:1103).
  • "Newest expandable pack" still means the last row; on healthy listings the sort is a no-op.
  • Prototype: frontier.sort(...) after each split → 0 existing tests changed (394 passed; only known red tests failed).
  • New tests needed: expansion order on a merged listing, and on a skip pack.

12Better plan

Order of work (tests first)

  1. Rewrite the odd-grain test for decision 4 = no.
  2. Add red tests: nap accepts a non-neighbor nearest pair; refuses across a nearer one; refuses unequal grain after "unknown id"; expanded wake order (merged listing, skip pack).
  3. Make gitutil.fold_ids balanced; plant ABD/ABE legacy shapes directly.
  4. summem: picker loop; pair check; grain check placement; expand sort with a full key.
  5. Docs: the six stale sites in §2 and §11.
  6. Optional: port the simulation as an opt-in slow check that reports stalls and misordering.

Corrections to the earlier proposal

  • Drop the heal-time opening of non-2ᵏ packs (decision 4).
  • Don't assert "every listed grain is 2ᵏ" — assert "every pack written is 2ᵏ" (already committed in b9dc459).
  • Put the grain refusal after child loading, not in the pair check, to keep error order.
  • Keep pull-back as a property the picker mostly has, not as a hard rule — as a hard rule it strands rows.

13Decision

Approve, with the corrections in §12

Oldest-pair-first is the only rule tested here that never stalled, kept 28 recent notes verbatim in both seeds, and listed the fewest notes above older ones in both seeds (on newer-above-older note pairs it was within 4% of the best in seed 7 and best in seed 11). Your three intuitions hold up under investigation: 2 = yes is required by the no-odd-grain rule (and "nearest" costs nothing); 3 = yes is display-only with zero test and zero store impact today; 4 = no costs nothing on this machine — no store has such a pack. The one open risk is that "no row strands forever" is simulated, not proven; a seeded property test is the cheap way to keep it true.
